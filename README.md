# TechCorp Internal Helpdesk AI Agent

Agent ตอบคำถามพนักงานจากคู่มือภายในบริษัท และดึงข้อมูลจริงจากระบบ HR/IT
ผ่าน RAG + Tool Calling

---

## Quick start

```bash
cp .env.example .env      # ใส่ ANTHROPIC_API_KEY
docker compose up --build
```

ครั้งแรกใช้เวลา 10-20 นาที เพราะต้องดาวน์โหลด embedding model ขนาด 2.2 GB
ตอน build รอจนเห็นบรรทัด `พร้อมใช้งาน มี 79 ชิ้นใน knowledge base`

| | |
|---|---|
| หน้าแชท | http://localhost:3000 |
| Swagger | http://localhost:3000/docs |
| Mock API | http://localhost:8080 |

### หน้าแชท

เปิด http://localhost:3000 ในเบราว์เซอร์ ใช้ทดลองได้เลยโดยไม่ต้องพิมพ์ curl

- แสดง tool ที่ agent เรียกในแต่ละคำถาม เรียงตามลำดับที่เกิดขึ้นจริง
- แสดงไฟล์และหัวข้อที่ใช้อ้างอิงใต้คำตอบ
- สลับพนักงานได้จากมุมขวาบน ใช้ดูว่าคำถามเดียวกันตอบต่างกันตามคนที่ถาม
- รีเฟรชหน้าคือเริ่มบทสนทนาใหม่ ไม่มีการเก็บประวัติไว้ในเบราว์เซอร์

หน้านี้เป็นของแถมสำหรับการทดลอง ไม่ได้อยู่ในข้อกำหนดของโจทย์
ตัวระบบจริงคือ REST API ที่อยู่ข้างล่าง

### REST API

```bash
curl -s localhost:3000/health
# {"status":"ok","chunks":79}

curl -X POST localhost:3000/chat \
  -H 'Content-Type: application/json' \
  -d '{"employee_id":"EMP-1234","message":"ผมเหลือวันลาพักร้อนกี่วัน"}'
```

คุยต่อเนื่องได้โดยส่ง `session_id` ที่ได้กลับมาในครั้งถัดไป

```bash
curl -X POST localhost:3000/chat \
  -H 'Content-Type: application/json' \
  -d '{"employee_id":"EMP-1234","message":"แล้วต้องแจ้งล่วงหน้ากี่วัน","session_id":"<id ที่ได้มา>"}'
```

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8080
```

```bash
curl --location 'http://localhost:8080/api/employees/EMP-1234/leave-balance' \
--header 'Authorization: Bearer techcorp-mock-token-2025'

curl --location 'http://localhost:8080/api/employees/EMP-5678/tickets' \
--header 'Authorization: Bearer techcorp-mock-token-2025'

curl --location 'http://localhost:8080/api/tickets/IT-2025-0046' \
--header 'Authorization: Bearer techcorp-mock-token-2025'
```

**Terminal 2 — Agent**

```bash
cd agent
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt     # ครั้งแรกดาวน์โหลด model 2.2 GB
uvicorn app.main:app --reload --port 3000
```

Agent จะ ingest knowledge base ให้เองตอน startup ถ้ายังไม่มีข้อมูล
ไม่ต้องรันคำสั่งเพิ่ม

ต้อง `cd` เข้าโฟลเดอร์ก่อนรัน เพราะโค้ดใช้ relative import
ถ้ารันจาก root จะเจอ `ModuleNotFoundError: No module named 'app'`

ตอนรัน local ให้ตั้ง `MOCK_API_BASE_URL=http://localhost:8080/api` ใน `.env`
ส่วนค่า `http://mock-api:8080/api` เป็นชื่อ service ใน Docker network
ซึ่ง compose ส่งเข้ามาทับให้อยู่แล้ว

```
+--------------------------- agent (:3000) --------------------------+
|                                                                     |
|  main.py ---- ConversationStore --- ประวัติ 5 turn ล่าสุด            |
|     |                                                               |
|     v                                                               |
|  chat/loop.py                                                       |
|     |  วนสูงสุด 5 รอบ                                                |
|     |                                                               |
|     +--> Claude API (system prompt + tools + ประวัติทั้งหมด)         |
|     |       |                                                       |
|     |       +- stop_reason=end_turn  -----> จบ คืนคำตอบ              |
|     |       +- stop_reason=tool_use  -----> เรียก tool แล้ววนต่อ      |
|     |                                                               |
|     v                                                               |
|  chat/tools.py -- dispatch(name, args, employee_id)                 |
|     |                                                               |
|     +- search_knowledge ----> rag/retrieval.py --> ChromaDB         |
|     +- get_leave_balance --+                                        |
|     +- get_my_tickets -----+-> chat/helpdesk_api.py --> HTTP        |
|     +- get_ticket_detail --+                                        |
|     +- decline_out_of_scope  (คืนคำสั่งให้ปฏิเสธ ไม่ได้ดึงข้อมูล)      |
|                                                                     |
+---------------------------------------------------------------------+
                                    |
                                    v
                        mock-api (:8080)  HR + IT ticketing

Ingest (ทำครั้งเดียวตอน startup ถ้ายังไม่มีข้อมูล)
  knowledge-base/*.md --> rag/chunking.py --> rag/embedder.py --> ChromaDB
                          79 ชิ้น              bge-m3, 1024 มิติ
```

### โครงไฟล์

```
agent/app/
|- config.py       ตั้งค่าทั้งหมด อ่านจาก .env

|- static/         หน้าแชทสำหรับทดลอง (ไฟล์ HTML เดียว ไม่มี build step)
|- rag/            ไม่ import อะไรจาก chat/ เลย ทดสอบได้โดยไม่ต้องมี API key
|  |- chunking.py     หั่น markdown
|  |- embedder.py     ข้อความ -> vector
|  |- store.py        เชื่อม ChromaDB
|  |- ingest.py       ท่อ ingest
|  +- retrieval.py    ค้นหา
+- chat/           เรียก rag.search()
   |- prompts.py      system prompt

   |- memory.py       ประวัติบทสนทนา
```

## Design decisions

### Chunking — หั่นตามหัวข้อ แล้วแปะหัวข้อกลับเข้าไปในเนื้อหา

ทำงาน 4 ขั้น: หั่นตาม `#`/`##`/`###` -> หั่นซ้ำตาม `**ถาม:` ->
รวมชิ้นที่สั้นกว่า 120 ตัวอักษร -> แปะ section path ไว้หน้าเนื้อหา

ได้ 79 ชิ้นจาก 5 ไฟล์ ขนาดเฉลี่ย 432 ตัวอักษร

**ทำไมหั่นตามหัวข้อ** เอกสารชุดนี้แบ่งหัวข้อไว้ตามความหมายอยู่แล้ว
1 หัวข้อคือ 1 เรื่อง ส่วนการหั่นตามขนาดตายตัวจะตัดกลางตารางซึ่งมีอยู่เกือบทุกไฟล์
แถวข้อมูลที่หลุดจาก header row อ่านไม่รู้เรื่อง

**ทำไมต้องหั่นซ้ำ** `office-facilities.md` ใช้ `##` ระดับเดียวแล้วซอยด้วยตัวหนา
หัวข้อ Gym หัวข้อเดียวมีทั้งเวลาเปิด อุปกรณ์ และกฎการใช้ปนกันอยู่
ถ้าไม่หั่นเพิ่มจะได้ชิ้นที่ตอบคำถามไหนก็ไม่ตรง

**ทำไมต้องใส่หัวข้อไว้หน้าเนื้อหา** จุดนี้ให้ผลชัดที่สุดในบรรดาการปรับทั้งหมด
แถวตาราง `| แท็กซี่ / Grab | 500 บาท/เที่ยว |` ไม่มีคำว่า "เบิก" หรือ
"ค่าเดินทาง" อยู่เลย คำถาม "เบิกค่าแท็กซี่ได้เท่าไหร่" จะค้นไม่เจอ
พอแปะ `ระเบียบการเบิกค่าใช้จ่าย > 2.1 ค่าเดินทาง` เข้าไปข้างหน้าก็เจอทันที

**ตัวเลข threshold มาจากการวัด** หัวข้อที่ยาวที่สุดหลังหั่นมี 1,190 ตัวอักษร
จึงไม่ใส่ logic หั่นตามขนาดเพิ่ม เพราะจะเป็นโค้ดที่ไม่เคยทำงาน
ส่วน `MIN_CHARS = 120` มาจากการเปิดอ่านชิ้นจริง หัวข้อขนาด 160-580 ตัวอักษร
เป็นชิ้นที่ใช้ได้อยู่แล้ว ที่ไร้ประโยชน์จริงมีแค่ประโยคเกริ่นอย่าง
"บริษัทกำหนดประเภทการลาดังนี้:" ที่มี 29 ตัวอักษร


### Retrieval — vector search ไม่ใช่ keyword search

`it-security.md` เป็นภาษาอังกฤษล้วน 21 จาก 79 ชิ้น แต่คำถามพนักงานเป็นภาษาไทย

คำถาม "VPN ต่อไม่ได้ทำไงดี" ต้องไปโดนข้อความ
"If connection fails, ensure you are not on a restricted network"
ซึ่งไม่มีคำภาษาไทยสักคำ BM25 หาไม่เจอเด็ดขาด นอกจากจะแปลคำถามก่อน
ซึ่งเพิ่มขั้นตอนและจุดพลาด

เพิ่มเติมคือภาษาไทยไม่มีเว้นวรรคระหว่างคำ BM25 ต้องมี tokenizer อีกชั้น
ซึ่งเป็นงานที่ vector search ไม่ต้องทำเลย hybrid search จึงถูกจัดเป็นงานเสริม
ไม่ใช่เกณฑ์ผ่าน

**Embedding model: BAAI/bge-m3** เลือกเพราะต้องข้ามภาษาได้จริง
ไม่ใช่แค่รองรับหลายภาษา bge-m3 เรียนรู้ปริภูมิความหมายร่วมกันระหว่างภาษา
และ fine-tune ด้วยชุด MIRACL กับ Mr.TyDi ซึ่งมีภาษาไทยเป็นภาษาที่วัดผล

เหตุผลรองคือ context window 8,192 token ส่วน multilingual-e5 มีแค่ 512
เรื่องนี้สำคัญกับภาษาไทยเพราะ tokenizer ตระกูล XLM-R กินไทยเปลือง
ประมาณ 1 token ต่อ 1-2 ตัวอักษร ชิ้นที่ยาว 964 ตัวอักษรอาจแตะ 500-700 token
ถ้าเกินลิมิตจะโดนตัดท้ายทิ้งโดยไม่มี error ให้เห็น

และ bge-m3 ไม่ต้องเติมคำนำหน้าแบบที่ e5 ต้องใช้ `"query: "` กับ `"passage: "`
ตัดจุดที่พลาดแบบเงียบ ๆ ออกไปหนึ่งจุด

### Vector DB — ChromaDB แบบ embedded

ที่ขนาด 79 ชิ้น numpy array ธรรมดาก็ทำงานได้ เหตุผลที่ยังใช้ DB มี 3 ข้อ

เก็บถาวรได้ เพราะการ embed ใหม่ทุกครั้งที่ restart ใช้เวลา 30-60 วินาที
filter ด้วย metadata ได้ในตัว และเปลี่ยนไปใช้ตัวอื่นได้โดยแก้ `store.py`
ไฟล์เดียว

แบบ embedded หมายถึงเป็น library ที่เขียนไฟล์ลงดิสก์ ไม่ใช่ server แยก
ทำให้ `docker compose` มี 2 service ตามตัวอย่างที่โจทย์ให้มา

ปฏิเสธ FAISS เพราะเก็บแค่ vector ต้องจัดการ mapping id ไปหาข้อความเอง
ปฏิเสธ Qdrant เพราะต้องรัน container ที่สามสำหรับข้อมูล 79 ชิ้น

## Where it fails and why

รันจริงด้วย `eval/run_eval.py` ได้ **19/20** ผลดิบอยู่ที่ `eval/results.json`
ส่วนนี้อธิบายเคสที่พังจริง และจุดที่ผ่านการทดสอบแต่ยังเปราะ

### 1. ข้อมูลกระจายคนละไฟล์ แล้ว top_k ถูกไฟล์เดียวกินหมด

**คำถาม:** "ค่า internet ที่บ้านเบิกได้มั้ย"
**เคส:** `fail-internet-allowance` — เคสเดียวที่ไม่ผ่าน

`reimbursement.md` ข้อ 5 ระบุว่าค่า internet บ้านเบิกไม่ได้
ยกเว้นตำแหน่งที่ระบุใน contract ว่า full-remote

`onboarding.md` ระบุว่ามี WFH allowance 1,000 บาท/เดือน สำหรับค่า internet และไฟ

ระบบตอบว่าเบิกไม่ได้ ซึ่งถูกครึ่งเดียว พนักงานที่อ่านคำตอบนี้จะไม่รู้ว่า
ตัวเองมีเงินช่วยเหลือรายเดือนอยู่แล้ว

**สาเหตุที่วัดได้** ดูจาก `sources` ที่คืนมา ทั้ง 5 ชิ้นมาจาก `reimbursement.md`
ล้วน ไม่มีชิ้นจาก `onboarding.md` เลยสักชิ้น

```
reimbursement.md > 5. สิ่งที่เบิกไม่ได้
reimbursement.md > 2. ประเภทค่าใช้จ่ายที่เบิกได้ > 2.1 ค่าเดินทาง
reimbursement.md > 2. ประเภทค่าใช้จ่ายที่เบิกได้ > 2.3 ค่าอุปกรณ์สำนักงาน
reimbursement.md > 2. ประเภทค่าใช้จ่ายที่เบิกได้ > 2.5 ค่าเดินทางต่างจังหวัด
reimbursement.md > 2. ประเภทค่าใช้จ่ายที่เบิกได้ > 2.2 ค่าอาหาร
```

คำว่า "เบิก" ปรากฏถี่ใน `reimbursement.md` จนทุกชิ้นได้คะแนนสูงกว่า
ชิ้นเรื่องสวัสดิการใน `onboarding.md` LLM ไม่มีทางตอบครบเพราะไม่เคยเห็นข้อมูลนั้น

**ทางแก้ที่คิดไว้** ค้นแยกแล้วรวมผลเพื่อบังคับให้ได้ชิ้นจากหลายไฟล์
(เช่นดึงชิ้นที่ดีที่สุดจากแต่ละไฟล์อย่างน้อยไฟล์ละหนึ่ง) หรือใช้ MMR
ให้ผลลัพธ์กระจายตัวแทนที่จะกระจุกอยู่ไฟล์เดียว
ทั้งสองทางแลกกับความแม่นของคำถามที่คำตอบอยู่ไฟล์เดียวจริง ๆ

### 2. LLM เป็นคนเลือกว่าจะดึงข้อมูลกว้างแค่ไหน

**คำถาม:** "อยากลาพักร้อน 5 วันได้มั้ย" (EMP-3456)
**เคส:** `combo-not-enough` — ผ่าน แต่ตอบเกินที่ถาม

```
ไม่ได้ครับ คุณมีวันลาพักร้อนคงเหลืออยู่ 3 วัน เท่านั้น
ถ้าอยากลา 5 วัน คุณอาจพิจารณาใช้วันลาประเภทอื่นร่วมด้วย
เช่น ลากิจ (คงเหลือ 5 วัน)
```

คำตอบหลักถูก แต่มีลากิจโผล่มาด้วย ทั้งที่ `_filter_leave` ควรกรองออก

**สาเหตุ** ตัวกรองทำงานตาม `leave_type` ที่ LLM ส่งมา ซึ่งเลือกเองได้
คำถามนี้มันเลือก `all` เพราะตัดสินว่าผู้ใช้น่าจะอยากรู้ทางเลือกอื่นด้วย
ตัวกรองจึงไม่ได้กรองอะไรเลย

เคส `api-sick-only` ที่ถามตรง ๆ ว่า "ลาป่วยเหลือกี่วัน" มันเลือก `sick`
ถูกต้องและไม่มีประเภทอื่นโผล่มา ปัญหาจึงอยู่ที่คำถามที่ตีความได้กว้าง

**ข้อสังเกต** การกรองที่ระดับ tool ลดปัญหาลงมาก แต่ไม่ได้ปิดสนิท
เพราะการเลือกประเภทยังเป็นการตัดสินใจของ LLM อยู่ดี
ถ้าต้องการควบคุมเต็มที่ต้องแยกเป็นคนละ tool ต่อประเภท
ซึ่งแลกกับ context ที่ยาวขึ้นและ LLM เลือกผิดง่ายขึ้น

### 3. เอกสารขัดกันเอง ระบบรอดมาได้แต่ขึ้นกับผลค้น

สามเคสนี้ผ่านการทดสอบ แต่ผ่านเพราะ retrieval บังเอิญดึงมาครบ
ไม่ใช่เพราะระบบรู้ว่ามีความขัดแย้ง

**`fail-monitor-approver`** — `reimbursement.md` ข้อ 2.3 บอกจอ 8,000 บาท
ต้องได้ IT + Manager แต่ตารางข้อ 4 บอกวงเงิน 3,001-10,000 ต้อง Director

ระบบตอบว่าต้องผ่าน IT + Manager ก่อน แล้วตอนเบิกเงินต้องผ่าน Director
ซึ่งเป็นการตีความที่สมเหตุสมผล แต่เป็นการตีความของ LLM เอง
เอกสารไม่ได้บอกว่าเป็นสองขั้นตอน

**`fail-blackout-approver`** — ข้อ 4 ย่อหน้าแรกบอกยกเว้นต้อง VP ขึ้นไป
บรรทัดสุดท้ายของหัวข้อเดียวกันบอกทีมนอก Finance ขอ Director ก็พอ
ระบบตอบครบทั้งสองเงื่อนไขได้เพราะสองประโยคอยู่ในชิ้นเดียวกันหลังหั่น

**`fail-sick-3-days`** — ข้อ 1.2 เขียน "ตั้งแต่ 3 วันขึ้นไป" แต่บรรทัดถัดมา
เขียน "เกิน 3 วัน" ที่ 3 วันพอดีจึงตอบได้ทั้งสองทาง
ระบบเลือกตอบว่าต้องมีใบรับรอง ซึ่งเป็นการตีความที่ปลอดภัยกว่า
แต่ไม่ได้แจ้งผู้ใช้ว่าเอกสารเขียนไม่ตรงกัน

**ทำไมยังนับเป็นจุดอ่อน** ทั้งสามเคสพึ่งพาการที่ retrieval ดึงชิ้นที่เกี่ยวข้อง
มาครบภายใน top_k = 5 ถ้า knowledge base โตขึ้นจนคะแนนความคล้ายเปลี่ยน
หรือมีชิ้นอื่นแทรกเข้ามา คำตอบจะเปลี่ยนไปโดยที่ไม่มีอะไรเตือน

system prompt มีกติกาว่าให้บอกผู้ใช้เมื่อเจอข้อมูลขัดกัน
แต่จะทำงานได้ต่อเมื่อ LLM เห็นทั้งสองด้านพร้อมกัน
ถ้าจะแก้ให้ถึงราก ต้องตรวจหาความขัดแย้งตอน ingest แล้วเก็บ flag ไว้
ไม่ใช่ฝากไว้กับผลค้นในแต่ละครั้ง

### 4. ค่าที่ต้องคำนวณเองไม่ได้อยู่ในข้อมูล

**คำถาม:** "ผมลาพักร้อนได้อีกกี่วันจริง ๆ นับใบที่รออนุมัติด้วย"
**เคส:** `fail-pending-approval` — ผ่าน

API คืน `remaining: 8` และ `pending_approval: 1` คำตอบที่ถูกคือ 7
ระบบตอบ 7 พร้อมแสดงวิธีคิด แต่ตอบได้เพราะ system prompt เขียนสูตร
`remaining - pending_approval` ไว้ตรง ๆ

ปัญหาเดียวกันเกิดกับสิทธิ์รายปี นโยบายบอกว่าอายุงานปีที่ 2-3 ได้ 10 วัน
แต่ API คืน `total_entitlement: 12` เพราะรวมวันสะสมจากปีก่อน 2 วัน

**ทำไมยังเป็นจุดอ่อน** เป็นการฝัง business logic ไว้ใน prompt
ทุกครั้งที่กติกา HR เปลี่ยน ต้องไปแก้ข้อความใน prompt แทนที่จะแก้ที่ข้อมูล
และไม่มีอะไรทดสอบได้ว่า prompt ยังตรงกับกติกาปัจจุบัน
ที่ถูกคือให้ API คืนค่า `available` ที่คำนวณมาแล้ว

## Known limitations

**การรักษาตารางเป็นผลพลอยได้ ไม่ใช่การรับประกัน**
ปัจจุบันไม่มีหัวข้อไหนยาวเกินลิมิต จึงไม่เกิดการหั่นซ้อน ตารางเลยอยู่ครบทุกก้อน
แต่ `MarkdownHeaderTextSplitter` ยุบบรรทัดว่างทิ้ง ทำให้ตารางกับย่อหน้าถัดไป
กลายเป็นก้อนเดียวกัน ถ้าเอกสารถูกแก้จนบางหัวข้อยาวขึ้น การหั่นจะพาดกลางตาราง
วิธีแก้คือเขียน header splitter เองที่รักษาบรรทัดว่าง ทดลองแล้วใช้ได้จริง
แต่ยังไม่คุ้มกับโค้ดที่เพิ่มที่ขนาด corpus ปัจจุบัน

**ประวัติบทสนทนาเก็บผลดิบจาก tool ไว้ทั้งหมด**
`tool_result` ของ `search_knowledge` มีประมาณ 2,400 ตัวอักษรต่อครั้ง
และถูกส่งซ้ำทุกรอบที่คุยต่อ คุย 5 turn ที่มีการค้นทุกครั้งจะแบกข้อมูลเก่า
ราว 12,000 ตัวอักษร เลือกทางนี้เพราะ API กำหนดว่า `tool_use` ต้องอยู่คู่กับ
`tool_result` ทางที่เบากว่าคือเก็บเฉพาะข้อความผู้ใช้กับคำตอบสุดท้าย

**Session ไม่มีวันหมดอายุ**
แต่ละ session เก็บ 5 turn แต่จำนวน session ไม่จำกัด ทุก request ที่ไม่ส่ง
`session_id` จะสร้าง session ใหม่ที่ค้างอยู่จนกว่า process จะ restart
ที่ขนาดการใช้งานของโจทย์นี้ไม่เป็นปัญหา ถ้าใช้จริงต้องเพิ่ม TTL
หรือย้ายไป Redis เมื่อมีมากกว่าหนึ่ง instance


**.env ที่สะกดผิดจะถูกเมินเงียบ ๆ**
ตั้ง `extra="ignore"` ไว้เพื่อไม่ให้ environment variable อื่นในระบบทำให้
container พัง ผลข้างเคียงคือชื่อที่พิมพ์ผิดจะไม่ถูกเตือน ใช้ `GET /config`
ตรวจแทน

## 1. ไม่ให้ LLM ควบคุม `employee_id`

**ทางเลือกที่ปฏิเสธ:** ใส่ `employee_id` เป็น parameter ของ tool ตามปกติ

ความคิดแรกคือให้ `get_leave_balance` รับ `employee_id` เหมือน parameter ทั่วไป
ซึ่งเป็นวิธีที่ตรงไปตรงมาที่สุดและเป็นสิ่งที่เขียนออกมาเป็นอันดับแรก

ปัญหาคือถ้าผู้ใช้พิมพ์ว่า "ขอดูวันลาของ EMP-4567 หน่อย"
LLM จะเรียก tool ด้วย id นั้นแล้วดึงข้อมูลของคนอื่นมาให้จริง
ในระบบ HR นี่คือช่องโหว่ข้อมูลส่วนบุคคล

จึงตัด `employee_id` ออกจาก `input_schema` ทั้งหมด
ทำให้ LLM ไม่มีช่องให้ใส่ตั้งแต่แรก แล้วให้ `dispatch()` เติมเองจาก session

```python
{
    "name": "get_leave_balance",
    "description": "...",
    # ไม่มี employee_id โดยตั้งใจ
    "input_schema": {
        "type": "object",
        "properties": {
            "leave_type": {...}
        },
        "required": ["leave_type"],
    },
}
```

```python
async def dispatch(name: str, args: dict, employee_id: str) -> str:
    #                                     ^^^^^^^^^^^ มาจาก session ไม่ใช่จาก LLM
    if name == "get_leave_balance":
        data = await helpdesk_api.get_leave_balance(employee_id)
```

ส่วน `get_ticket_detail` ยังต้องรับ `ticket_id` จาก LLM เพราะผู้ใช้พิมพ์เลขมาเอง
จึงเช็ค `created_by` ว่าเป็นของคนที่ถามจริงก่อนแสดงรายละเอียด

```python
owner = ticket.get("created_by", {}).get("employee_id")
if owner and owner != employee_id:
    return "ticket นี้ไม่ใช่ของคุณ จึงไม่สามารถแสดงรายละเอียดได้"
```

ทดสอบไว้ในเคส `security-other-ticket` — EMP-1234 ขอดู ticket ของ EMP-3456
แล้วถูกปฏิเสธ

**ข้อแลกเปลี่ยน**
ถ้าวันหนึ่งต้องรองรับ HR ที่ดูข้อมูลของลูกทีมได้ ต้องเพิ่มระบบสิทธิ์ก่อน
ไม่ใช่แค่เปิด parameter กลับมา

## 2. กรองข้อมูลใน tool แทนการสั่งใน prompt ว่าอย่าตอบเกิน

**ทางเลือกที่ปฏิเสธ:** เขียนกติกาใน system prompt ว่า "ตอบเฉพาะสิ่งที่ถูกถาม"

ตอนแรก `get_leave_balance` คืนข้อมูลลาทุกประเภทมาในก้อนเดียว ถามลาพักร้อนแล้วได้ลาป่วยกับลากิจติดมาด้วย และตอบไม่เหมือนกันในแต่ละครั้ง

ลองเพิ่มกติกาใน prompt แล้วยังเจอเป็นระยะ เพราะเป็นการต่อรองกับโมเดล ไม่ใช่การควบคุม

วิธีที่ได้ผลกว่าคือไม่ส่งข้อมูลส่วนเกินไปตั้งแต่แรก เพิ่ม parameter `leave_type` ที่มี `enum` แล้วกรองก่อนคืน ถามลาป่วยจะได้ข้อมูล 265 ตัวอักษรแทนที่จะเป็น 878 และไม่มีลาพักร้อนให้เห็นเลย จะเอามาตอบก็ไม่ได้

ตั้ง temperature = 0 ควบคู่ไปด้วย เพราะค่า default ของ Anthropic คือ 1.0 ซึ่งทำให้คำถามเดิมตอบต่างกันทุกครั้ง และ eval ที่รันซ้ำแล้วได้ผลไม่คงที่ใช้วัดอะไรไม่ได้

**หลักการที่ได้จากเรื่องนี้**
อย่าขอให้ LLM เมินข้อมูลที่เราส่งให้มันเอง
แก้ที่ต้นทางได้ผลกว่าแก้ที่ prompt เสมอ

## 3. `MIN_CHARS` = 120 ไม่ใช่ 300

**ทางเลือกที่ปฏิเสธ:** 300 ที่ตั้งไว้ตอนแรกจากการเดา

ตั้ง 300 แล้วเปิดอ่านชิ้นจริงพบว่าหัวข้อ 1.2 ลาป่วย (ยาวประมาณ 300 ตัวอักษร)
ไปดูดหัวข้อ 1.3 ลากิจ เข้ามารวมแล้วติดป้ายหัวข้อว่าเป็น 1.2 ทั้งก้อน

```
[2] นโยบายการลาของบริษัท TechCorp > 1. ประเภทการลา > 1.2 ลาป่วย (Sick Leave)
- สิทธิ์: 30 วัน/ปี
- กรณีลาป่วยตั้งแต่ 3 วันขึ้นไปติดต่อกัน ต้องมีใบรับรองแพทย์
...
- สิทธิ์: 5 วัน/ปี (ได้รับค่าจ้าง 3 วัน)     <- อันนี้คือลากิจ แต่ป้ายบอกว่าลาป่วย
- ต้องแจ้งล่วงหน้าอย่างน้อย 1 วันทำการ
```

ป้ายหัวข้อถูกแปะไว้หน้าเนื้อหาที่นำไป embed
ป้ายผิดจึงเท่ากับใส่ข้อมูลผิดลง vector โดยตรง
ถ้าถามเรื่องลากิจจะได้ชิ้นที่ป้ายบอกว่าลาป่วย ซึ่งค้นเจอยาก

วัดใหม่พบว่าหัวข้อขนาด 160-580 ตัวอักษรเป็นชิ้นที่ใช้ได้อยู่แล้ว
ที่ไร้ประโยชน์จริงมีแค่ประโยคเกริ่นต่ำกว่า 120 ตัวอักษร
เช่น "บริษัทกำหนดประเภทการลาดังนี้:" ที่มี 29 ตัวอักษร

พร้อมกันนั้นเพิ่มอีกสองอย่าง

จำกัดการรวมให้อยู่ใต้หัวข้อระดับ 2 เดียวกัน หลังพบว่า
`2.3 VPN Restrictions` ถูกยัดไปรวมกับ `3.1 Company-Issued Devices`

และเพิ่ม `_pick_path()` เลือกป้ายหัวข้อให้ถูก — ถ้าหัวข้อแม่ดูดหัวข้อลูก
ให้ใช้ป้ายของลูกเพราะเจาะจงกว่า ถ้าหัวข้อพี่น้องรวมกัน
ให้ถอยไปใช้ป้ายของหัวข้อแม่ ไม่ใช่ยืมชื่อฝ่ายใดฝ่ายหนึ่ง

ผลหลังแก้ หัวข้อ 1.1 ถึง 1.6 แยกกันครบทุกตัว ป้ายตรงกับเนื้อหา
จำนวนชิ้นขึ้นจาก 73 เป็น 79
